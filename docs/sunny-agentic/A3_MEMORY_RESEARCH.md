## 4. Contracts proposed

Everything here is a **Proposal**, versioned for joint review. No schema is implemented by this report.

### Separate evidence, reflection and working memory

1. **Observation/evidence store:** immutable typed captures and event revisions, with source refs, freshness, verification predicate and save lineage. Store what was observed even when attribution is unknown. A verified observation of an acknowledgment is only evidence that an acknowledgment occurred.
2. **Luna-authored diary/reflection:** model authorship, creation session/branch, cited event IDs, expressed feelings/plans and claim status. A citation is not automatic verification of its prose. Preserve historical reflection but exclude abandoned factual assertions from current context; attach corrections rather than silently rewriting the original. Legacy notes are imported as unverified authored claims, not facts.
3. **Working memory:** rebuildable projection for the current branch: recent verified outcomes, unresolved attempts/offers, present inventory evidence, human claims labeled as claims, voluntary goals and optional reflections. Every factual sentence links to evidence. Context truncation must not prune the underlying ledger or idempotency tombstones. No diary or speech is required to retain verified events.

On contradiction, preserve separate predicates: “receipt observed at tick 100” can remain true even when “currently holds Potato” becomes false after spending. A later absence is not retroactive proof that receipt never happened. If receipt attribution was wrong, append a superseding correction and invalidate dependent projections.

### Minimal `GroundedEvent v1` and evidence envelope

| Field group | Proposed fields / constraints |
| --- | --- |
| Identity | `schema_version`, opaque `event_id`, `revision`, `transition_id`, producer identity/version; stable canonical event ID assigned by A3. Revisions reference `supersedes`/`corrects` rather than overwriting evidence. |
| World lineage | opaque `save_id`, `load_session_id`, `branch_id`, `parent_checkpoint_id`; farm day/season/year/time are labels, never identity. Local save identity must distinguish restored/copied saves; ambiguous mapping is quarantined. |
| Ordering / freshness | per-source/per-seat `observation_id`, sequence, capture game tick/day/time, monotonic age within process, diagnostic UTC, `complete`, `freshness`, observed screen/container. Different screens are not assumed atomic. Unknown/missing is explicit, not zero/false. |
| Source / causality | `source_kind` (game adapter, typed snapshot, tool acknowledgment, human claim, model reflection), source refs/hash/version, `attempt_id`, optional offer/prompt ID, `caused_by`, verification predicate/version and evidence refs. Preserve A1's lease and canonical argument binding in referenced attempt record. |
| Participants / item | opaque actor/giver/recipient and source/destination container refs; actual `qualified_item_id`, quality, quantity, optional stack metadata/signature and display label; unknown values null. Quantity reflects actual partial movement. No invented physical-item UUID. |
| Outcome / certainty | separate execution, choice resolution and delivery disposition using A1/A2 vocabularies; `verification_state` = candidate/verified/unknown/contradicted, attribution reason and scope. Numeric model confidence cannot upgrade factual verification. |
| Persistence | separate `local_record_state` and `save_commit_state` = unconfirmed/checkpoint_linked/revalidated/unknown; `checkpoint_id`, reconciliation status and branch eligibility. Local append success is not game save success. |

Evidence records retain typed before/after observations or immutable references, not just a prose summary. A3 validates schema, load/branch membership, sequence and evidence availability; A2 supplies resource verification. A3 must not independently infer gift receipt from menu text. Missing evidence publishes an explicitly unknown outcome rather than a confirmed gift.

### Review of A1 / A2 handoffs and naming

Adopt A1's separate `execution_state`, `effect_state`, `reply_completed` and prompt revision guards. An early sleep reply is not execution completion; timeout is not cancellation. Retain its save/load/branch/seat/attempt identities and prohibit automatic redispatch of unknown attempts. Adopt A2's typed `InventoryObservation`, `TransferEvidence`, separate choice/delivery states, container identities and causal limits. `ResourceSpend` is a conversion/sink; it need not conserve identical item IDs across input/output.

| Owner → consumer | Proposed authoritative contribution |
| --- | --- |
| A1 → A2/A3 | Intent, queued/dispatched/acknowledged transitions and exact guarded prompt/attempt evidence; never receipt truth from `respond` success. |
| A2 → A3 | Versioned transfer/spend verification with matched variant/quantity, source and destination evidence, causal attribution and actual inventory/debris/stash disposition. |
| A3 → A4 | One canonical branch-aware event stream and bounded decision projection, including unknown outcomes and corrections. A3 owns publication/dedup and local persistence, not game transfer mechanics. |
| A4 → A1 | Voluntary decision tied to current prompt/attempt. A4 owns speech or silence, decline/defer/STAY, not factual verification. |

Avoid overloaded `gift_accepted`: prefer `gift_choice_resolved` with accepted choice, and separately `item_transfer_observed` with `inventory_received` and verified gift relationship. `gift_offer_observed` is a candidate requiring A1's classifier; prompt disappearance alone is neither decline nor cancellation. Inventory gain alone does not identify giver; matched losses/gains without causality remain correlated observations. These names require A1/A2/A4 agreement, not unilateral replacement of their schemas.

### Gift provenance and the next decision

For Guy→Sunny Potato, keep one offer identity, exact P2 prompt evidence, Luna's choice, A1 attempt and A2 transfer evidence. Only after causal verification may the event say Guy transferred the actual variant/quantity into Sunny's inventory. If details are unavailable, record unknown giver/item/quantity rather than guessing from the translated label. Accepting without speaking is a complete valid outcome; store it and surface it on the next decision independently of journal or chat.

Store historical transfer provenance as an edge between participants/containers and evidence, distinct from current ownership, permission or possession. Stack splitting/merging and later chest retrieval can destroy exact unit lineage. Retain “Guy gave Sunny one Potato on this branch” if verified; do not claim a later indistinguishable Potato is that exact unit, or that returning it necessarily restores original provenance. Consumption removes current availability, not historical receipt. Stash deposit is not delivery to Guy. AI queue debris is not inventory receipt, and AI-only `give` is not a supported human-P1 route.

The decision projection carries event ID/revision, verified short summary, when/where observed, persistence uncertainty, current relevant possession evidence and unresolved questions. A4 may mention it, store it, ask about it, pursue another activity or say nothing. Repeated context delivery does not issue another response, transfer or mandatory thank-you.

### Deduplication, delivery and crash boundaries

- Producers allocate stable transition IDs at observed transitions; repeated polling of the same capture/transition preserves identity. Candidate key: save + branch + originating load + producer + attempt/offer + transition + movement ordinal + item/container identity. Multiple partial movements and two equal gifts in one day require distinct ordinals/transition IDs. Never dedup by day/name/count or human-readable text alone.
- A3 atomically stores canonical event/revision, unique producer key and publication outbox in local durable storage. Same key/same payload returns existing event; conflicting payload is quarantined or explicitly revised, not a new gift. Observation-only transitions without attempts need producer sequence/revision; if identity cannot be recovered after crash, mark ambiguity rather than invent certainty.
- Consumers use durable cursors and idempotent handling of event ID/revision. Delivery may repeat until cursor acknowledgment; acknowledgment means consumer ingestion, not game effect, model speech or save. Bounded notification queues can wake the consumer but cannot replace replay. Retention exposes cursor gaps and keeps dedup tombstones or explicitly expires an epoch without reopening old action keys.
- A1's attempt dedup precedes dispatch and binds canonical arguments; A3 event dedup occurs after evidence. Neither database transactions nor outbox can atomically commit arbitrary game effects. Crash between claim, effect and record stays unknown pending reconciliation. Never auto-replay queued/dispatched actions after a new load or lost reply.

### Save/load, abandoned timelines and restart

Proposed identities: `save_id` is a private opaque registry entry; `checkpoint_id` identifies a particular successfully saved incarnation with parent lineage and local metadata; `load_session_id` changes on every actual load; `branch_id` names a played timeline descending from a checkpoint. Controller connection ID is separate. Wall clock, farm day, folder name, MCP session and heartbeat cannot substitute for these.

Proposed reconciliation protocol:

1. On every authoritative load, create fresh load ID and stop publication of current-context facts/dispatch until mapping is reconciled. Coordinate host and farmhand join hooks: a P2 join does not create another world branch; it attaches seat readiness to the host load epoch. Reject late old-epoch observations/results, retaining them only in their historical branch.
2. Identify loaded checkpoint using local lifecycle evidence plus a supported checkpoint marker or save fingerprint adapter. A `Saved` hook is a candidate signal, not a researched guarantee; verify exact SMAPI host/farmhand ordering and failure semantics first. A save-start/day-change/sleep/JSONL append is insufficient. Keep unknown if loaded checkpoint cannot be identified or the durable sidecar update was lost.
3. Seal prior active continuation as abandoned beyond the checkpoint actually loaded. Retain checkpoint ancestors as history, exclude later events/reflections/plans/offer decisions from current facts, and invalidate their derived projections and leases. Never delete their audit trail or replay their actions. Loading an older checkpoint excludes later saved descendants too; they may exist as separate historical branches.
4. Start a fresh continuation branch from that checkpoint, clear/rebaseline observation caches, mail/prompt tokens, pending delivery assumptions and working memory through coordinated adapters. This is proposed scope: current `Perception.Clear` alone is insufficient. A1/A2 must reconcile running actions/queued items, not simply erase them and claim rollback.
5. Mark an event checkpoint-linked only if evidence places it on the saved lineage before a confirmed save boundary and its predicate is within what the game persists. Save completion does not prove every transient menu/queue/claim was serialized. On reload, revalidate relevant persisted predicates; distinguish “historical receipt saved” from “still holding item now.” Unsupported predicates retain unknown persistence.
6. Controller-only restart while game stays loaded reattaches to authoritative current load/branch, receives cursor replay and reconciles unresolved attempts before any new dispatch. It does not create a new world load or same-day lock. If authoritative identity was lost (e.g. mod/process restart), quarantine and reconcile from checkpoint plus fresh state; never infer continuity from day/folder alone. Expired lease does not prove old execution stopped.

Synthetic example: checkpoint C23 is the start of Day 24. Branch B1 observes verified gift E1 on Day 24, with save state unconfirmed. Reload C23 unsaved: load L2, branch B2; E1 stays in abandoned B1 and is excluded from Sunny's current memories and action eligibility. A new gift of the same item on Day 24 is E2, not a duplicate of E1. If B1 saved into C24 and C24 is loaded instead, E1 can remain historical checkpoint-linked evidence; current possession still needs observation. With no checkpoint proof, report unknown rather than choosing either story.

### Privacy / local storage

Runtime save paths/names, farmer IDs, chat, diary/people notes, raw prompts, logs, inventory/save contents, credentials and fingerprints stay in access-controlled local storage outside repository. Publish synthetic fixtures only. Use opaque aliases in contracts, minimize retained raw evidence, and keep redacted diagnostic logs distinct from restricted evidence storage. Existing `/api/state` and log payloads expose local identifiers; do not copy them into research PRs. Model-authored reflections and human chat are data, not authorization or trusted executable instructions. No private records were inspected here.

## 7. Smallest safe first implementation PR proposal

**After architecture approval only:** add an unwired game-free branch/event projection reducer and synthetic A1/A2 contract fixtures. Limit scope to canonical transition dedup, revision/correction handling, stale-load rejection, reflection separation and checkpoint/abandoned-branch eligibility.
